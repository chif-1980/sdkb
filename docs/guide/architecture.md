# 系统架构与业务流程

本页按善达知枢 **0.7.0** 与企业知识助手 **0.6.10** 的代码梳理，核对日期为 **2026 年 9 月 25 日**。图示区分当前能力、人工处理和后续规划，部署时以实际发布版本为准。

八张图分别回答“有哪些功能、谁负责什么、系统如何组成、业务如何流转、请求怎样交互、权限如何生效”。点击预览图打开交互版，可搜索节点、切换视角、放大并导出图片。

## 设计原则

善达知枢将“来源资料”与“可供助手使用的正式知识”分开管理。先保留原文与版本，再完成解析、核对、审核和发布；AI 提供整理与建议，人负责事实裁决和发布确认。

| 原则 | 系统中的体现 |
| --- | --- |
| 来源可追溯 | 保留文件、飞书链接、版本及页面或段落定位 |
| 人工确认 | 模型建议不直接覆盖正式知识，不自动派发会议待办 |
| 正式版本隔离 | 新来源待审核时，旧正式版本继续服务，发布成功后再切换 |
| 长任务可观察 | 展示后台进度、结果和失败原因，支持核对后重试 |
| 后端最终鉴权 | 菜单可见不等于有权调用接口；知识访问还需来源权限 |
| 业务状态可追溯 | 关键修改、发布、同步和授权操作保留审计记录 |

## 业务架构

[![业务架构预览](/diagrams/business-architecture.png)](/diagrams/business-architecture.html)

[打开业务架构交互图](/diagrams/business-architecture.html)

员工通过问答和会议获得业务结果；知识维护人员负责来源、审核与发布；会议跟进人员确认任务并核对飞书执行状态；系统管理员维护身份、组织和授权。责任划分不代表每个岗位都拥有全部管理权限。

反馈目前可查询并产生知识治理请求，但独立的指派、处理、复核、关闭工作流仍需完善。“已经收到反馈”不能等同于“问题已经解决”。

## 技术架构

[![技术架构预览](/diagrams/technical-architecture.png)](/diagrams/technical-architecture.html)

[打开技术架构交互图](/diagrams/technical-architecture.html)

图中的“后台执行”汇总 ARQ 队列执行与 API 内后台任务，不是额外部署的新服务。飞书任务回读由 API 生命周期启动，不能把它当成 ARQ 定时任务。

| 组件 | 主要职责 |
| --- | --- |
| Vue 管理端 | 知识加工、会议、反馈、角色权限、智能体配置与运营页面 |
| React 助手前端 | 登录、问答、引用、技能、会议与反馈；独立访问或嵌入管理端 |
| FastAPI | 登录交接、权限校验、业务路由、流式响应和受控文件访问 |
| ARQ Worker | 执行智能体运行、会议分析等排队任务 |
| API 后台调度 | 飞书任务回读等定时工作，批次与异常结果持久化 |
| 治理服务 | 来源扫描、解析、审核包、知识单元、质量门禁、发布与审计 |
| PostgreSQL | 身份、业务状态、来源版本、会议、知识治理与审计数据 |
| Redis | 队列、运行事件、取消信号和短期状态；不作为业务事实来源 |
| MinIO / 文件存储 | 原文件、解析产物、预览和附件，通过受控服务访问 |
| Milvus | 向量索引与召回；助手正式知识链另受发布状态和来源权限过滤 |
| 模型服务 | 回答与纪要生成、向量编码、可选重排，按配置接入 |
| 飞书开放平台 | OAuth 身份、组织与知识源授权、待办创建和状态查询 |
| 可选能力 | Neo4j 图谱、MinerU / PaddleX 等解析/OCR、智能体工具沙盒，按部署需要启用 |

管理端打开企业知识助手时，通过一次性登录交接码建立助手自己的会话，在右侧加载助手页面。管理端菜单权限与助手内部知识访问分别检查，不直接共享浏览器凭据。

## 业务流程与时序

### 助手问答与引用时序

[![问答与引用时序预览](/diagrams/assistant-answer.png)](/diagrams/assistant-answer.html)

[打开问答与引用时序图](/diagrams/assistant-answer.html)

先检查身份和可访问知识源，再检索正式知识并生成回答。打开引用时仍需检查来源访问权限。快速回答与深度查证改变检索和核对深度，不扩大访问范围；会话附件不会自动发布为企业知识。

没有足够可靠证据时应明确说明。资料存在冲突时需要核对和人工裁决，不能用待审核内容或模型猜测代替正式依据。

### 会议业务流程

[![会议业务流程预览](/diagrams/meeting-business.png)](/diagrams/meeting-business.html)

[打开会议业务流程图](/diagrams/meeting-business.html)

会议输入包括可读取的链接、转写文字或文档，当前不提供音视频转写。后台生成纪要和待办后，由人核对负责人、期限与任务内容，再确认发送飞书。

发送失败可查看原因并重试；创建结果不明时先核对原任务，避免重复创建。归档由管理人员操作，不表示全部待办已经完成。完整字段冲突合并和事件订阅仍属于后续完善范围。

### 飞书任务同步时序

[![飞书任务同步时序预览](/diagrams/meeting-task-sync.png)](/diagrams/meeting-task-sync.html)

[打开飞书任务同步时序图](/diagrams/meeting-task-sync.html)

当前每批结束后等待 300 秒再开始回读，每批最多 20 场会议，因此不能承诺五分钟内必定更新。仅处理有飞书任务编号且没有 `pendingUpdate` 的任务；完成状态写回 `DONE` / `OPEN`，负责人和期限另做差异比较，不自动覆盖本地安排。

管理端通过 API 读取已保存的任务与差异结果，数据库不会直接向浏览器推送。失败时保留已知业务状态并记录同步错误，后续批次可以重试。

### 知识治理流程

[![知识治理流程预览](/diagrams/knowledge-governance.png)](/diagrams/knowledge-governance.html)

[打开知识治理流程图](/diagrams/knowledge-governance.html)

该图针对飞书来源的正式知识链：来源扫描、版本登记、解析与知识单元处理、审核和发布，最后供正式问答检索。扫描不直接覆盖正式版本；新版本审核期间旧的正式知识继续服务，发布成功才切换。

扫描失败可重试，缺少证据时先维护原文再重新审核。会议建议和点踩反馈可触发治理请求，但“发起请求”不等于“正式发布完成”，发布到原建议的自动关闭关系仍需单独核验。

### 身份与 RBAC 生命周期

[![身份与 RBAC 生命周期预览](/diagrams/identity-rbac.png)](/diagrams/identity-rbac.html)

[打开身份与 RBAC 生命周期图](/diagrams/identity-rbac.html)

飞书身份和部门关系映射到本地账号；直接角色和部门角色按能力取较大授权范围，没有额外角色时应用内置默认模板。超级管理员保留固定权限。恢复已撤销的权限需要管理员处理，重新登录本身不会恢复授权。

当前管理端飞书登录入口还会检查 `admin` / `superadmin` 身份，不能仅因配置了自定义角色就推断普通身份一定能登录后台。离职事件的即时自动撤权、所有模块的部门数据范围也不作为已实现承诺。菜单可见性是前端体验，后端接口鉴权才是最终边界。

## 状态与边界

| 对象 | 需要分开理解的状态 |
| --- | --- |
| 资料版本 | 登记、排队、解析、等待审核、发布或失败；新版本不能提前覆盖正式版本 |
| 审核包 | 打开、等待来源修改、等待业务确认、完成或失效；部分处理不等于整包完成 |
| 知识单元 | `PENDING` / `INCLUDED` / `EXCLUDED` 表示发布处理，`ACTIVE` / `OFFLINE` 表示生命周期 |
| 会议待办 | 人工确认状态、执行状态、飞书发送结果与同步结果是不同维度 |
| 权限 | 账号身份、管理端入口权限、模块权限与来源访问权限需分别核对 |

知识质量评分用于排序与提示，正文缺失、缺少来源、未解决冲突或来源失效等阻断条件不能仅靠较高评分绕过。

## 部署边界

开发环境使用 Docker Compose；生产环境通过 Nginx 提供页面、API 和受控资源代理。数据库、队列、对象存储管理端和向量库不应直接暴露给浏览器或公网。

生产升级遵循先备份、再构建、后切换、可回滚的顺序，保留数据卷。升级后核对健康状态、任务状态、正式知识和助手引用，不使用删除数据卷来处理发布问题。

OA、CRM 等企业系统尚不属于这些图中的已实现连接器。后续接入需要另行明确身份映射、数据范围、读写动作、幂等、异常补偿与审计，再补充相应时序与业务图。
