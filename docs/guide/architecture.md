# 设计哲学与系统架构

本页描述当前善达知枢的稳定边界和业务原则。实现细节会随版本演进，部署时请以实际发布版本的变更记录为准。

## 我们解决什么问题

企业资料通常分散在飞书、文件服务器和各种办公文件中。直接把原文丢给模型会带来三个风险：资料是否最新不清楚、回答无法回到原文、不同文件的重复和冲突没人负责。

善达知枢把“资料”与“可被助手使用的知识”分开管理：先保存来源，再解析为知识单元，经过证据核对和质量门禁，最后才进入正式检索。这样，AI 可以承担发现、归并、比较和提示，人仍然掌握发布与事实裁决权。

## 设计哲学

| 原则 | 在系统中的体现 | 带来的好处 |
| --- | --- | --- |
| 来源优先 | 原始文件、飞书链接、版本和页面/段落定位始终保留 | 每条知识都能追溯，出现争议时可以回到原文 |
| 知识单元优先 | 审核粒度是有业务含义的知识单元，而不是孤立分块 | 可以局部发布和局部退回，减少重复劳动 |
| AI 建议、人来裁决 | AI 负责相似度、变化摘要、质量评分和建议动作；纳入、排除、冲突裁决仍需人工确认 | 自动化提效，同时避免未经确认的内容进入正式知识 |
| 正式知识可回滚 | 版本切换、下架、恢复和来源变更均形成追加式事件 | 更新失败时旧版本继续可用，治理动作可解释 |
| 安全自动化 | 观察模式先记录结果，再逐步启用系统提醒、飞书通知和安全自动关闭 | 新策略可以先验证再放量，不因自动化误操作影响业务 |
| 异步但可观察 | 扫描、解析、索引和发布由后台任务执行，前端显示阶段、当前资料和失败原因 | 长任务不阻塞页面，运营者知道系统正在做什么 |
| 最小权限 | 飞书只读同步、后端最终鉴权、前端同源代理和隔离沙盒 | 降低凭据泄露和横向访问风险 |

### 组件职责

| 组件 | 主要职责 | 典型入口 |
| --- | --- | --- |
| Vue 管理端 | 知识源、扫描、审核工作区、跨文档检查、正式知识和运营待办 | `manager` 管理端或本地 `5173` |
| 知识助手前端 | 登录、提问、流式回答、引用展开和反馈 | `assit` 助手或本地 `5174` |
| FastAPI | 认证、权限、业务路由、SSE/轮询和文件预览 | `/api/*` |
| ARQ Worker | 扫描、资料解析、跨文档比较、索引和发布任务 | Redis 队列中的后台任务 |
| 治理服务 | 审核包、知识单元、质量门禁、关系裁决、审计和通知 | `/api/governance/*`、`/api/feishu-knowledge/*` |
| PostgreSQL | 用户、来源、版本、知识单元、审核、事件和通知元数据 | 业务事实与状态的持久化来源 |
| MinIO | 原文件、解析产物、页面/幻灯片预览和图片资源 | 私有对象存储；前端通过受控代理访问 |
| Milvus | 已发布知识的向量索引和检索 | 只接收正式知识内容 |
| Neo4j（可选） | 知识图谱节点与关系 | 需要图谱能力时启用 |
| MinerU / PaddleX | 复杂文档解析、版式还原和 OCR | 由 API/Worker 调用 |
| Redis | 任务队列、运行事件、取消信号和短期状态 | 不作为业务事实来源 |

## 两条核心链路

### 资料到正式知识

```text
飞书知识源
  → 增量/全量扫描
  → 版本登记与原文件归档
  → 解析、版式/OCR、内容块切分
  → 知识单元归并与跨文档比较
  → 审核包与质量门禁
  → 人工纳入/排除/退回/冲突裁决
  → 发布、索引和正式知识
```

扫描只负责发现和登记，不会绕过审核直接覆盖正式知识。来源发生变化时，旧的正式版本继续服务，新的版本进入待审核；发布成功后才切换活动版本。

### 正式知识到助手回答

```text
用户问题
  → 产品登录与知识源权限校验
  → 向量召回（必要时重排/图谱辅助）
  → 仅使用正式、有效、可追溯的知识
  → 生成回答与引用
  → 用户展开引用或反馈
  → 可定位的反馈回流治理待办
```

当没有足够可靠的正式资料时，助手应明确返回“暂无足够可靠资料”，而不是用待审核内容补答。若正式来源之间存在未解决冲突，回答会提示资料冲突，运营者应先完成跨文档裁决。

## 状态与边界

- **版本状态**：资料版本经历登记、排队、解析、等待审核、发布排队、发布中、已发布或失败等阶段。
- **审核包状态**：`OPEN`、等待来源修改、等待业务确认、`COMPLETED`、`INVALIDATED`。一个审核包可以包含多个知识单元，部分处理后仍保持打开。
- **知识单元状态**：`PENDING`、`INCLUDED`、`EXCLUDED` 等发布状态与 `ACTIVE`/`OFFLINE` 生命周期状态分别表达“是否进入检索”和“当前是否可用”。
- **跨文档关系状态**：开放关系必须先处理，尤其是冲突关系；关系裁决会写入双方资料的审计记录。
- **质量门禁**：评分用于排序和提示，硬性阻断项优先级更高；正文为空、缺少来源位置、存在未解决冲突或来源失效时不能发布。

## 部署拓扑

开发环境使用 Docker Compose 提供 API、Worker、管理端、数据库、队列、对象存储和检索服务；前端源码通过 Vite 热更新。生产环境使用固定镜像和 Nginx，同源代理 `/api` 与公开对象路径，不把 PostgreSQL、Redis、MinIO 或 Milvus 端口直接暴露给公网。

生产升级遵循“先备份、再构建、后切换、可回滚”原则：只重建本次变更的 API/Worker/Web 服务，保留数据卷；升级后检查健康状态、任务状态、正式知识数量和助手引用，不使用删除数据卷的方式解决部署问题。
